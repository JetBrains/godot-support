# Poly Symbols in GDScript

## Summary
In my opinion, the use of Poly Symbols brings a framework better suited for the implementation of the GDScript language. It will lead to a code base that will be less error-prone, and more self-reliant by removing the bundling of the GDScript SDK with Rider. It will also allow for more natural communication with TSCN elements. 

The current implementation of Poly Symbols in GDScript is not complete and has some missing features and issues that need to be addressed. Currently, it works for the most part in cases where the PSI is still active, the symbols are there only to replace the SDK, but the PSI handles the rest. Even in that case, they still need more testing to ensure there are no regressions compared to the old SDK.

## What are Poly Symbols
[Poly Symbols](https://plugins.jetbrains.com/docs/intellij/polysymbols.html) is a new framework based on the [Symbols platform API](https://plugins.jetbrains.com/docs/intellij/symbols.html).
The Poly Symbols framework, in contrast with plain Symbols, is designed to provide a rich experience out-of-the-box. A poly symbol can be seen as an abstraction similar to a PSI element, though it is not necessary for PSI to be involved (like in the SDK-based symbols that come from XML files, and for which we use a custom parser `GdSdkXmlParser`). Poly Symbols help implement features we currently do through PSI, which is why I will refer to the old language implementation as the "PSI implementation", but this doesn't mean that we won't use the PSI anymore. The GDScript parser still returns PSI, and we will use PSI utilities to implement PSI-based poly symbols under the hood, but the consumers, like the annotators, will only interact with symbols and the PSI layer will be hidden. The consumers won't need to care if the symbol comes from a GDScript, XML, or TSCN file. 

Symbols are served through scopes. You contribute certain scopes in certain PSI locations (`GdPolySymbolQueryScopeContributor`). This dictates what symbols are available in that specific location. A symbol can contribute its own scopes as well. For example, in a `GdRefIdRef` location, we contribute all SDK classes. In turn, these classes have a scope of their own that contains all its methods, properties, constants, enums, signals, etc. An enum has a scope of its own that exposes all of its enum values. We can chain these scopes to get qualified references. A symbol `ReferencingPolySymbol` can also represent a group of symbols e.g. a symbol of kind TYPE_HINTS is a reference to other symbols of kind CLASS, LOADED_CLASS_ALIAS, and ENUM, which is all available symbol kinds in a type hint. To consume the symbols, you run query executors to get symbols of a certain type and name, or all symbols of a certain type, given certain scopes.

Once you define the symbols and the scopes correctly, it is straightforward to use them to define reference resolution. Once you have resolution, other features like code completion, find usages, and rename refactoring, come easily or the framework handles it by itself already in the latter cases.

To get started, you need to define a Poly Symbol class (GdPolySymbol) that contains information about:
- **What the symbol represents:** The name, kind, return type, icon, text shown in completion contexts, etc.
- **What scopes it exposes:** For a class, for example, the methods, constructors, properties, constants, signals, and the scopes of their parents in the inheritance chain.
- **How to interact with it:** You can override the default behavior for things like its target presentation, search target, rename target, documentation target, and navigation target. For PSI-based symbols, the default behavior is usually what you want. SDK-based symbols require more customization by their nature of coming from XML files. For example, we decided to override the navigation target for SDK symbols by creating a synthetic PSI file on demand and navigating there on Go To declaration.

Then, you can provide them through an already existing scope or define a new scope contributor (`GdPolySymbolQueryScopeContributor`) that contributes scopes in certain PSI locations.

## GDScript SDK
The SDK-based Poly Symbols are divided by the Core SDK and GDExtension SDK. We can generate the docs (XML files) by calling the Godot executable with certain flags. Core SDK comes from the `--doctool` flag and it is given by Godot itself. It changes only on Godot version updates and can be shared among different projects, which is why it is stored in the plugin directory. On the other hand, GDExtensions are extensions coming from Godot's marketplace and are project-specific. People can also have their own documentation in XML files for their own extensions, or they can be generated by the `--doctool --gdextension-docs` flags. 
It was [an idea](https://jetbrains.team/p/ij/reviews/207019/files) to run these commands as a run configuration. I think this presents some unwanted friction, especially in the case where the whole SDK is generated through poly symbols, which is why I returned to the use of a background post-startup activity (`GdLoadSdkProjectActivity`), though I didn't have time to clean up this approach. We can refine this idea or find another way of generating the docs. 

### Singletons
Godot's doc XMLs carry no singleton marker: an engine singleton like `Input` looks exactly like any other `Object`-derived class, and so does a GDExtension-registered one. What makes `Input` work is that `@GlobalScope.xml` declares `<member name="Input" type="Input">` — all of its members are self-typed, so that file is nothing but the engine's singleton list expressed as global variables. `gdSdkGlobalPolySymbolScope` turns them into `GdSdkPropertySymbol`s, and the property's return type is the one hop that leads back to the class symbol.

GDExtension singletons are exposed the same way instead of through a dedicated symbol kind. `GdLibraryManager` runs `gdscript/scripts/dump_singletons.gd` in a headless Godot instance (the only source of truth: `Engine.get_singleton_list()` plus `ClassDB.class_get_api_type()`), and `GdGlobalSingletonsDocWriter` renders the `api_type >= 2` entries into a generated `@GDExtensionScope.xml`. From there the existing SDK pipeline does everything: resolution, return type inference, instance members, docs, navigation and highlighting work unchanged. A distinct pseudo-class is used rather than a second `@GlobalScope.xml`, because two SDK files sharing a class id would break `GdSdkPropertySymbol.createPointer`, which re-resolves its data through that id.

Consequences worth knowing:
- `GdPolySymbolsConstants.GLOBAL_CLASSES` is the single place that lists the global pseudo-classes; membership also keeps them out of class completion and drives the built-in-global coloring.
- The name collision described below stays, and with it `checkGlobalStaticMatch`: this design deliberately *extends* the `@GlobalScope` accident to GDExtension singletons instead of removing it. An alternative design modelling singletons as their own `GdPolySymbolKind.SINGLETON` is recorded in commit `c126dc0`.
- A bare singleton name matches both the global variable and the class of the same name, and resolving to two kinds at once makes the platform's `asSingleSymbol()` give up, which looks exactly like an unresolved reference. `GdPsiPolySymbolUtil.preferGlobalVariableOverClass` (applied in `GdRefIdRefImpl`) drops the class, and `GdSdkPropertySymbol.syntheticSourceElement` sends a self-typed global variable to its class, so Go To Declaration still lands on something useful.
- The dump runs Godot in editor mode (`--headless --editor`), because editor-only extension singletons (`api_type == 3`) are registered only there; the editor singleton list is a superset of the runtime one, so one run covers both kinds. Editor-only singletons therefore end up offered in every file, not just in `@tool` scripts.

## What's Implemented
The current implementation combines both the PSI and Poly Symbols approaches. We would get rid of the PSI implementation when the Poly Symbols approach is fully functional. 
- We have reference resolution and navigation working for class-level contexts, meaning it works for any reference to the SDK, as the user cannot edit the SDK code itself, only reference the classes and their members. There may be some missing cases that were not tested, but it works for the most common cases. 
- Code completion works, although there might be some extra completion items that shouldn't be present. It also doesn't deduplicate with the LSP-provided completion items, so they appear doubled. 
- Syntax highlighting, find usages, and rename refactoring work for elements that resolve to symbols, with some minor issues.

## What's Missing
### To Fix Current Poly Symbols Implementation
- There is a decision to be made on how to generate the XML files. It can be the automatic generation through the post-startup activity or the run configuration. If we choose the post-startup activity, there are some changes needed, like the way to get the version of Godot we are using changed to a service. There are some comments on the files in the `gdscript.library` package that explain further. I know that Ivan Sachov has made some progress towards generating these files and converting them to GDScript files. I'm not sure what his approach to this problem was.
- The caching system for the SDK still needs work. The entire `GdSdkParseCache` gets invalidated too often. We probably need a custom stamping system to only invalidate when actually necessary. Currently, everything depends on the single `GdSdkDocsTracker`, which is bumped after every generation and on any VFS change under the generated doc directories, so touching one XML invalidates the whole SDK.
- The tracking part of `GdSdkDocsTracker` needs to be replaced with whatever will be the system to keep track of modifications to the SDK.
- If an element is resolved by both the PSI and the Poly Symbols, you get double Find Usages targets from the reference; from the declaration you only get the PSI one. This shouldn't matter if we get rid of the PSI completely.
- In the `@GlobalScope.xml` file, there are properties with the same name as the classes they represent e.g. `var Input: Input`. This means that `Input` can refer both to the class or to the variable in the global scope. Look at the PSI implementation for information on how these cases should be handled.
- I didn't find the best way to deal with static access. I tried using modifiers on the queries, but they didn't seem to propagate past the referencing symbols. I ended up filtering the results after the query with helpers in `GdPolySymbolScopeUtil`.
- I did not finish testing that only the correct scopes are exposed at all times, which is why code completion was not included in the "polished" branch. I already know of a problem where the inner classes should not expose the members of the outer class when accessed from outside. This means that while you are inside a file (all files in GDScript are classes, even if you don't declare them as such. `class_name` gives it a name, `class` defines an inner class) with `class_name Outer:` and `class Inner:` inside it, the code from inside `Inner` can reference the members of `Outer` e.g. `outer_method()`, but from another file you should not be able to do `Outer.Inner.outer_method()`
- In general, I didn't test the scopes of inner classes thoroughly. It is likely there are more problems there with inheritance.
- Code completion is contributed by the Godot LSP, but it is richer if we can do it through the poly symbols. LSP completion items don't provide icons and return types. If we provide code completion through the poly symbols, we also need to fix the problem of doubled items.
- If you place the caret at the end of an SDK symbol, you don't get the identifier highlighted through the local find usages e.g. Vector2\<caret>
### To Replace PSI Entirely
- To be able to replace the PSI reference contributors, we need to support local contexts with Poly Symbols as well. Currently, they only work with class-level contexts, but we still need scopes for blocks like methods, loops, etc. Kinds `BINDING_PATTERN`, `FOR_VARIABLE`, `LOCAL_VARIABLE`, and `PARAMETER` are not implemented in the reference resolution path yet. Resources (`GdResourceReferenceContributor`) are also not represented as symbols yet. I recently added a `GdKeyNmi` for the PSI that represents the keys of dictionaries and is resolved in `GdClassMemberReferencce`. They also would need to be represented as symbols.
- I'm not sure that `PsiGdExprUtil.getReturnType` returns the correct type in all cases involving Poly Symbols. The whole return type system would still need to be migrated towards Poly Symbols entirely anyway.
- Constructor symbols aren't really implemented. There needs to be a link between calling `new()` on a class and the `init()` method. Example: You instantiate a class by doing `MyClass.new(argument1, argument2)`, but the constructor is defined inside MyClass as `func _init(argument1, argument2):`. For SDK classes like `Vector2`, you instantiate it by doing `Vector2(arg1, arg2)` instead, but this is only true for Core SDK types like Vector2, Vector3, int, float, etc, not for GDExtensions. Currently, constructors also incorrectly appear in the code completion even when it's not static access.
- We need to represent the enum values of unnamed enums as symbols. There is `GdPsiEnumValueSymbol` and `GdSdkEnumValueSymbol`, but these are not contributed separately from their enum parent. Either contribute them as well if the enum is unnamed or create a new symbol type for unnamed enum values. They should be treated like a constant.
- I did not replace the implementation of annotations in places like `GdAnnotationAnnotator` with the use of `GdAnnotationSymbol` yet. It shouldn't be too complicated now, though.
- We should aim to replace the `config` package entirely. It is only there to parse through the .gdconf files that we created through the old method of generation of GDScript files from the XML with the PHP scripts. It's to have information on the operations and annotations of GDScript, which should be replaced entirely by `GdAnnotationSymbol` and `GdOperatorSymbol`.
- We need to use Poly Symbols for the TSCN language implementation as well. TSCN uses the GDScript stub indexes and the GDScript implementation uses some stub indexes from TSCN as well. The TSCN implementation is not very robust, so I trust it's not going to be too time-consuming to replace.
- We need more robust testing. In an ideal case, we can migrate the existing PSI tests to Poly Symbols to make sure everything that worked before still works, but there is still a gap in testing in the existing PSI implementation.
